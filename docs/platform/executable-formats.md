# NSO0 ingestion

The implemented executable format is NSO0 version zero. NRO, ELF, encrypted containers and newer ZBIC/zstd compression (flag bit 7) are not accepted as executables; package containers are identified separately by `intake`. Switchbrew is a public reverse-engineering reference, not Nintendo's official specification: [NSO0 revision 14440](https://switchbrew.org/w/index.php?title=NSO0&oldid=14440), [NRO0 revision 14196](https://switchbrew.org/w/index.php?title=NRO0&oldid=14196).

The 0x100-byte NSO header identifies text, rodata and data through file offsets, module-relative memory offsets and decoded sizes. Bits 0–2 select raw LZ4 block compression. Bits 3–5 require SHA-256 checks of decoded segments. Bit 6 produces execute-only text; bit 7 and unknown flags are rejected. Stored compressed sizes come from 0x60–0x68; an uncompressed segment uses its decoded size. BSS immediately follows data in guest memory and is not stored in the file. Build ID is preserved as 32 bytes; the complete input receives a separate SHA-256 fingerprint.

Validation checks magic, version, file bounds, decoded-size equality, enabled hashes, pairwise file/memory overlaps, module-name bounds, instruction alignment of text, BSS overlaps and rodata metadata ranges. Relative segment endpoints may not overflow 32 bits. File input, reconstructed memory extent and total decoded bytes are bounded to 512 MiB. Allocation and file-reading failures are explicit errors. All segment ranges are validated before decompression.

The module-name fields and embedded/dynstr/dynsym ranges are retained as metadata; the dynsym range also bounds the symbol table when a module has no `DT_HASH`. Absence of a recognized MOD0 header does not establish absence of relocation requirements: an arbitrary raw-like NSO can lack conventional module metadata.

For conventional MOD0 discovery, text word 1 is treated as a module-relative header location, and the target must contain `MOD0`. Signed offsets relative to MOD0 locate the dynamic table, BSS bounds, `.eh_frame_hdr` bounds and rtld's module-object storage. The dynamic table is read as 64-bit tag/value entries up to `DT_NULL` (at most 4096 entries), then interpreted and validated: string, symbol, hash and relocation tables must be mapped and consistent, and every relocation must reference an existing symbol. The complete rules are in [module loading](module-loading.md). Malformed dynamic metadata rejects the module.

A single NSO file with MOD0 relocations is refused by code generation, because executing it without relocation would expose unrelocated pointers. Load it as a process instead: a directory of ExeFS-named modules is placed and linked by `wl-loader`.

[libnx's entry source](https://github.com/switchbrew/libnx/blob/feebd026ca0f5dcc2119f46ad8e0d16ad3dd4973/nx/source/runtime/switch_crt0.s) demonstrates the module-header pointer and self-linking before runtime initialization; retail applications instead start in rtld, which links every module (see [module loading](module-loading.md)). The loader does not implement NRO asset trailers, external symbol lookup through `nn::ro`, TLS, initializer execution or ASLR.

NSO has no process-entry field. For a single file, `--entry` is mandatory: an absolute guest virtual address after adding the selected module base. For a process, the entry is the start of the first module's text, the Horizon convention. Inspection reports module-relative addresses and, with `--json`, a dynamic-metadata summary (needed libraries, symbol counts, relocation counts by type, `DT_REL(A)COUNT`, initializers).
